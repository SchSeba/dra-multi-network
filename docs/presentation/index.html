04 / EXPOSURE POLICY · PHYSICAL COMPATIBILITY

A PF and its VFs are mutually exclusive.

Exclusive PF handoff conflicts with its child VFs. Different VFs can coexist.

Host PF handoff + VF 0

Same family; groups do not intersect.

BLOCKED
VF 0 + VF 1

Same family; both are host-retained.

COMPATIBLE*
VF active → request host PF handoff

Conflict works in both allocation directions.

BLOCKED

* Subject to per-VF ownership, available capacity and other selectors.

Scheduler checks ResourceSlice compatibility; the node rechecks live ownership before mutation.

06 / NETWORKTOPOLOGY · YAML

The YAML defines the dependency graph.

Allocation steps request resources. Operation steps compose their outputs.

DUAL-VF-BOND-VLAN · NETWORKTOPOLOGY EXCERPT
apiVersion: networking.dra-multi-network.schseba.github.io/v1alpha1kind: NetworkTopologymetadata: {name: dual-vf-bond-vlan}spec:  effectBudget:    allow:    - linux/create-bond/v1    - linux/attach-master/v1    - linux/create-vlan/v1  steps:  - {id: left, kind: Allocation, pluginRef: {name: sriov-cni}}  - {id: right, kind: Allocation, pluginRef: {name: sriov-cni}}  - id: uplink    kind: Operation    pluginRef: {name: bond-cni}    inputs:      members: [{from: left.interface}, {from: right.interface}]    config: {ifName: bond0, mode: active-backup}  - id: tenant100    kind: Operation    pluginRef: {name: vlan-cni}    inputs: {parent: {from: uplink.interface}}    config: {ifName: tenant100, vlanId: 100}
Abbreviated: selectors, required config fields, other effects / VLANs / tuning omitted.
01 / EFFECT BUDGET

Bound the whole graph

effectBudget.allow caps the requested mutations across every step. Plugin permissions and device policy also apply.

02 / ALLOCATION ROOTS

left + right → two classes

Each Allocation root produces a DeviceClass. Selectors constrain hardware; config describes the requested interface.

03 / OPERATION + REFERENCES

Wire outputs into inputs

left.interface + right.interface feed the bond. uplink.interface feeds the VLAN. Config sets behavior; references determine execution order.

13 / IPAM · TOPOLOGY → DRA

IPAM is a DRA allocation root.

The topology declares the root. A ResourceClaim triggers Kubernetes allocation.

MACVLAN-IPAM · NETWORKTOPOLOGY EXCERPT
apiVersion: networking.dra-multi-network.schseba.github.io/v1alpha1kind: NetworkTopologymetadata: {name: macvlan-ipam}spec:  effectBudget:    allow: [linux/create-macvlan/v1,            linux/link-configure/v1, linux/address-configure/v1]  steps:  - id: endpoint    kind: Allocation    pluginRef: {name: macvlan-cni}    config: {ifName: secondary0, mtu: 1500, up: true,             mode: bridge, linkType: ethernet}  - id: address    kind: Allocation    pluginRef: {name: ipam}    config: {network: blue, subnet: 192.0.2.0/29}  - id: configure-address    kind: Operation    pluginRef: {name: address-cni}    inputs:      interface: {from: endpoint.interface}      lease: {from: address.lease}    config: {}
Hardware / persona selectors omitted; full example targets approved secondary devices.
01 / ADDRESS ALLOCATION ROOT

pluginRef: ipam

The approved plugin descriptor sets allocationDriver to ipam.schseba.github.io. Core generates an address-root DeviceClass.

02 / REQUEST THROUGH DRA

Subnet device → address share

IPAM publishes the subnet in ResourceSlices. The claim requests one address-capacity unit; Kubernetes allocates a share, then the provider reserves its concrete IP.

03 / COMPOSE THE OUTPUTS

Interface + lease → configured IP

endpoint.interface and address.lease feed address-cni. This Operation creates no additional DeviceClass or DRA request.

01 / SELECT THE ADDRESS POOL

blue · 192.0.2.0/29

CEL selects the IPAM driver and approved subnet. The complete class also requires a shared, allocation-ready device.

02 / LOCK THE TOPOLOGY ROOT

Class-origin configuration

The network driver receives the revision binding and rootStep: address. Users cannot substitute claim-supplied configuration.

03 / RESERVE ONE ADDRESS

IPAM backend configuration

The IPAM driver receives network, subnet and addresses: 1. Capacity lives in ResourceSlices; the provider reserves the concrete IP during preparation.

Two allocation roots. One complete network before containers start.

RESOURCECLAIM · MACVLAN + ONE ADDRESS
apiVersion: resource.k8s.io/v1kind: ResourceClaimmetadata: {name: macvlan-ipam, namespace: ipam-example}spec:  devices:    requests:    - name: endpoint      exactly:        deviceClassName: ENDPOINT_CLASS        allocationMode: ExactCount        count: 1        capacity:          requests:            dra-multi-network.schseba.github.io/children: "1"    - name: address      exactly:        deviceClassName: IPAM_CLASS        allocationMode: ExactCount        count: 1        capacity:          requests:            ipam.schseba.github.io/addresses: "1"
Class names are placeholders from topology.status.rootClasses.
The shipped example generates this claim from a ResourceClaimTemplate.
01 / ENDPOINT_CLASS

One macvlan child

count: 1 selects one shared parent device; children: "1" consumes one child-capacity unit.

02 / IPAM_CLASS

One address-capacity unit

count: 1 selects one subnet device; addresses: "1" consumes one IP unit. It does not select or configure a specific IP.

03 / RUNTIME JOIN

Interface + lease → address

Provider reserves the IP; address-cni uses endpoint.interface + address.lease. Exhausted subnet capacity keeps the claim Pending.
